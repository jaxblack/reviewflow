> **文档定位**：本文用于评审完整目标设计，不替代当前 PostgreSQL MVP 的验收报告。当前实现范围、已通过测试和剩余生产化差距见 [README](../README.md)。

| 项目 | 内容 |

## 2. 评审目标

评审需要回答以下问题：

1. 身份、角色、作者关系和资源可见性是否只能由服务端可信数据决定。
2. 内容工作副本、提交快照、审核轮次和审核决定是否边界清晰。
3. LOW、HIGH、多轮重提和任意拒绝的状态转换是否唯一且可解释。
4. 并发提交、并发审核、重复请求和失败回滚是否仍能保持数据库不变量。
5. API、数据库约束和应用事务是否形成互补防线，而不是依赖前端行为。
6. 测试方案能否使用真实 PostgreSQL 重复证明上述结论。

## 3. 评审范围

### 3.1 范围内

- 用户角色叠加、作者权限、自审禁止和管理员能力。
- `contents`、`content_revisions`、`review_rounds`、`review_decisions` 和 `idempotency_requests`。
- 创建、编辑、提交、审核、拒绝后重提、详情和历史查询。
- 单页统一工作区，以及 ADMIN 创建用户、改名和叠加角色。
- 状态机、乐观锁、行锁、唯一约束、幂等和事务回滚。
- OpenAPI/Zod 契约、错误语义、列表分页和前端能力字段。
- 数据库账号边界、不可变历史和输出转义。
- 单元、集成、并发、故障注入和端到端测试设计。

### 3.2 范围外

- 真实登录和身份提供方集成。
- 真实登录、用户删除、通知、审核 SLA、内容删除、撤回和申诉。
- 微服务拆分、消息队列、事件溯源和跨区域容灾。
- 未定义指标前的容量规划和性能 SLA。

范围外能力不得通过预留半成品字段或未验证流程影响当前核心事务。

## 4. 评审原则

### 4.1 单一可信身份

写操作中的 actor 必须来自 `getCurrentUser()`。任何请求体、路径扩展字段或前端缓存中的用户 ID 都不是可信身份。

### 4.2 单一业务写入口

创建、编辑、提交和审核分别由明确的命令服务负责。Controller 只处理协议转换、Schema 校验和错误映射，不复制状态机或权限判断。

### 4.3 工作副本与审核快照分离

`contents` 是当前可编辑工作副本；`content_revisions` 只在提交时生成不可变快照。审核轮次引用快照，不读取后来被修改的工作副本。

### 4.4 正确性由多层共同保证

- API Schema 拒绝未知字段和非法输入。
- 应用服务执行角色、作者、状态和跨表规则。
- PostgreSQL 事务、行锁、唯一索引、外键和 CHECK 约束提供最终防线。
- 自动化测试通过真实数据库验证，而不是只验证 mock 调用。

### 4.5 失败不得留下部分事实

审核决定、轮次终态、内容状态和幂等响应必须全部提交或全部回滚。任何只能靠补偿任务修复的正常业务路径都不通过评审。

## 5. 评审输入和证据

### 5.1 设计评审输入

- 当前系统设计文档及其 14 条业务不变量。
- 数据库 migration 和种子数据。
- OpenAPI 文档及 Zod Schema。
- 领域策略、命令服务和数据库事务代码。
- [reviewflow-test-plan.md](./reviewflow-test-plan.md) 及测试结果。
- 并发测试日志、失败注入结果和 CI 记录。

### 5.2 进入详细评审的最低条件

- 所有未明确需求已记录默认决定。
- 数据库 migration 可以在空库执行并可回滚或重建。
- Alice、Bob、Chen、Diana 使用固定 UUID 初始化。
- 核心 API 已有请求和响应示例。
- 每条不变量至少映射到一个自动化测试。

缺少以上任一项时，可以进行方案讨论，但不能给出最终“通过”结论。

## 6. 评审流程

### 6.1 阶段和门禁

| 门禁 | 评审主题 | 必须提交的证据 | 通过条件 |
| --- | --- | --- | --- |
| G0 | 需求和假设 | 不变量、边界决定、非目标 | 无相互冲突或未定的核心规则 |
| G1 | 领域模型 | 状态机、ER 图、关键流程 | 多轮审核与历史快照语义闭合 |
| G2 | 权限和契约 | 权限矩阵、OpenAPI、错误码 | 客户端不能伪造身份或状态 |
| G3 | 数据完整性 | migration、约束和索引 | 可由数据库保证的规则均有防线 |
| G4 | 事务和并发 | 锁顺序、事务代码、并发测试 | 竞态只能产生一个合法结果 |
| G5 | 查询和页面 | 查询条件、能力字段、转义策略 | 不越权、不混淆工作副本与历史 |
| G6 | 测试和交付 | 测试报告、CI、启动说明 | P0/P1 用例通过且可重复执行 |

任一门禁发现 P0 问题时停止后续批准流程；可以继续讨论修复方案，但结论只能是“不通过”。

### 6.2 建议会议安排

| 时间 | 内容 |
| ---: | --- |
| 10 分钟 | 目标、范围、角色和默认假设 |
| 15 分钟 | 逐条确认不变量和状态机 |
| 20 分钟 | ER、DDL、不可变快照和查询模型 |
| 25 分钟 | 提交、审核、幂等、锁顺序和竞态走查 |
| 10 分钟 | API、可见性和前端缓存边界 |
| 10 分钟 | 测试证据、问题分级和评审结论 |

复杂争议应记录为评审问题，不在会议中临时扩大系统范围。

## 7. 详细评审清单

### 7.1 需求与领域模型

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-DOM-01 | 角色是叠加关系 | ADMIN 不自动拥有 REVIEWER；多角色不绕过自审禁令 |
| TR-DOM-02 | 内容状态转换完整 | 只有 DRAFT/REJECTED 可编辑和提交，APPROVED 为终态 |
| TR-DOM-03 | 提交语义唯一 | 每次成功提交恰好产生一个 revision 和一个 round |
| TR-DOM-04 | 审核阈值冻结 | round 保存 `required_approvals`，历史不重新读取当前风险策略 |
| TR-DOM-05 | 拒绝语义明确 | 任意合法 REJECT 结束 OPEN 轮次，已有 APPROVE 历史保留 |
| TR-DOM-06 | 重提隔离 | 新轮次只统计自身 `round_id` 下的决定 |
| TR-DOM-07 | 工作副本和快照分离 | 编辑 REJECTED 内容不会修改历史 revision |
| TR-DOM-08 | 终态唯一 | round 和 content 不可能分别表示 APPROVED 与 REJECTED |

### 7.2 身份、权限与可见性

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-AUTH-01 | 当前用户来源 | 所有写服务只读取服务端会话，不读取 DTO 中的用户 ID |
| TR-AUTH-02 | 严格 DTO | `actorId`、`authorId`、`reviewerId`、status、roundNo 等未知字段返回 400 |
| TR-AUTH-03 | 作者权限 | 编辑和提交同时校验 SUBMITTER、作者关系和允许状态 |
| TR-AUTH-04 | 审核权限 | 同时校验 REVIEWER、非作者、当前轮次和本人未决定 |
| TR-AUTH-05 | 管理员权限 | ADMIN 可以查看全部内容，但没有隐式审核能力 |
| TR-AUTH-06 | 历史可见性 | 作者、ADMIN、当前合法审核人和曾参与审核者符合既定规则 |
| TR-AUTH-07 | 资源枚举策略 | 无权查看统一采用 403 或 404，契约和实现保持一致 |
| TR-AUTH-08 | ADMIN 用户管理 | 非 ADMIN 不可写；最后 ADMIN 不可移除；ADMIN 不隐式获得 REVIEWER |

### 7.3 数据模型和数据库约束

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-DB-01 | revision 归属 | 组合外键保证 round 引用同一 content 的 revision |
| TR-DB-02 | 单一 OPEN 轮次 | 部分唯一索引覆盖 `review_rounds(content_id) WHERE status='OPEN'` |
| TR-DB-03 | 单人单轮一次 | `UNIQUE(round_id, reviewer_id)` 存在并有约束测试 |
| TR-DB-04 | 拒绝理由 | API、服务和 CHECK 都拒绝 null、空串及纯空白理由 |
| TR-DB-05 | 轮次完成时间 | OPEN 对应 null，终态对应非 null |
| TR-DB-06 | 序号并发安全 | `MAX + 1` 在 content 行锁内执行，并由唯一约束兜底 |
| TR-DB-07 | 历史不可变 | 运行账号对 revision/decision 没有业务 UPDATE/DELETE 路径 |
| TR-DB-08 | 索引匹配查询 | 作者列表、状态列表、OPEN 队列、轮次历史和决定时间线均有索引支持 |
| TR-DB-09 | 审计姓名 | revision 和 decision 保存操作发生时的显示名快照 |
| TR-DB-10 | 数据库账号边界 | migration、应用和只读账号权限分离，PUBLIC 无表写权限 |

### 7.4 事务、锁和幂等

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-TXN-01 | 固定锁顺序 | 所有写路径遵循 idempotency → content → round |
| TR-TXN-02 | 锁后重验 | 角色事实之外的作者、状态、版本、轮次和已有决定在锁内重读 |
| TR-TXN-03 | 关闭轮次 CAS | 终态更新包含 `WHERE status='OPEN'` 并断言更新一行 |
| TR-TXN-04 | 通过数范围 | 只统计当前 round 的不同合法 APPROVE 决定 |
| TR-TXN-05 | 原子写入 | decision、round、content 和 idempotency response 位于同一事务 |
| TR-TXN-06 | 幂等范围 | 主键为 actor、operation、key，请求摘要覆盖方法、路径和规范化 body |
| TR-TXN-07 | 幂等重放 | 相同 key/摘要返回原状态码和响应；不同摘要返回 409 |
| TR-TXN-08 | 新 key 重复决定 | 相同语义返回已有记录，冲突语义返回 `ALREADY_DECIDED` |
| TR-TXN-09 | 回滚语义 | 任一中间点异常后，不留下业务记录或幂等记录 |
| TR-TXN-10 | 聚合版本 | 所有会使旧客户端视图失效的内容变更都推进 `lock_version` |
| TR-TXN-11 | 角色撤销 | 同一事务按剩余票数和未决定合法审核人检查所有 OPEN 轮次；已有合法票继续有效 |

### 7.5 API、查询和前端边界

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-API-01 | HTTP 语义 | 400/401/403/404/409/422 的使用在 OpenAPI、代码和测试中一致 |
| TR-API-02 | 乐观锁 | PATCH 和 submission 都要求 `expectedVersion` |
| TR-API-03 | 能力字段 | capabilities 由服务端计算，执行命令时仍重新校验 |
| TR-API-04 | 稳定分页 | 列表采用包含唯一 ID 的稳定排序和游标 |
| TR-API-05 | 待审查询 | 排除作者和本人已决定的 round，只返回 OPEN + IN_REVIEW |
| TR-API-06 | 历史读取 | 历史始终读取 round 对应 revision，不读取当前工作副本 |
| TR-API-07 | 用户切换 | 切换会话后清空或失效用户相关 Query Cache |
| TR-API-08 | 内容输出 | 正文按纯文本或安全 Markdown 输出，不直接执行存储 HTML |
| TR-API-09 | 统一工作区 | 当前身份的语义队列按内容 ID 去重，队列归属和详情可见性一致 |
| TR-API-10 | 用户管理 DTO | 名称和角色严格校验，重复名称、重复角色及未知字段有稳定错误 |
| TR-API-11 | PC 工作台效率 | 排序、筛选、快捷键、审计导出和成功提示只消费已授权响应，不旁路服务端权限、状态与事务 |

### 7.6 测试和可交付性

| ID | 检查项 | 通过标准 |
| --- | --- | --- |
| TR-TEST-01 | 数据库真实性 | 行锁和部分索引测试使用真实 PostgreSQL，不使用其他数据库引擎替代 |
| TR-TEST-02 | 并发可控 | 使用独立连接和屏障制造锁竞争，不只依赖普通 `Promise.all` |
| TR-TEST-03 | 双重断言 | 并发测试同时检查 HTTP 结果和最终数据库事实 |
| TR-TEST-04 | 故障注入 | decision 后、状态后等关键位置可注入异常并验证整体回滚 |
| TR-TEST-05 | 多轮主线 | E2E 覆盖拒绝、编辑、重提、第二轮通过和管理员历史查看 |
| TR-TEST-06 | 可重复执行 | 空环境可完成 migration、seed、测试和构建 |

## 8. 必须现场走查的五条链路

### 8.1 HIGH 内容首次提交

1. Alice 以服务端会话身份提交 DRAFT。
2. 事务认领幂等键并锁定 content。
3. 校验作者、SUBMITTER、状态和 expectedVersion。
4. 排除 Alice 后确认至少有两位不同 REVIEWER。
5. 创建 revision、OPEN round，并将 content 更新为 IN_REVIEW。
6. 推进 `lock_version`，保存幂等响应后一起提交。

评审重点：任何失败都不得留下孤立 revision、round 或未完成幂等结果。

### 8.2 HIGH 第二票通过与拒绝并发

1. round 已有 Bob 的一票 APPROVE。
2. Chen APPROVE 与另一合法 REVIEWER 的 REJECT 同时进入。
3. 两个事务按相同顺序竞争 content 和 round 行锁。
4. 首个成功提交者形成唯一终态。
5. 后获得锁者重读终态，返回 409，且不插入 decision。

评审重点：不能先插入决定再在事务外判断终态。

### 8.3 拒绝后编辑并重新提交

1. Round 1 终态为 REJECTED，历史决定和 revision 1 保留。
2. Alice 编辑 `contents` 工作副本，revision 1 不变。
3. 再次提交创建 revision 2 和 round 2。
4. Round 2 的进度从 0 开始，只统计自身决定。

评审重点：详情页和历史页不得混用工作副本与提交快照。

### 8.4 响应丢失后的幂等重试

1. 首次请求已提交业务事务，但客户端未收到响应。
2. 客户端使用同一个 key 和相同请求重试。
3. 服务端返回保存的原始状态码和响应体。
4. 数据库中没有新增 round 或 decision。

评审重点：幂等结果必须与业务事实同事务提交。

### 8.5 旧标签页跨越完整审核轮次

1. 标签页 A 持有旧 `expectedVersion`。
2. 标签页 B 提交内容，内容随后被拒绝。
3. 标签页 A 再尝试 PATCH。
4. 即使状态重新回到可编辑的 REJECTED，旧版本也必须收到 409，而不能覆盖新工作副本。

评审重点：提交和拒绝等状态变更必须使旧聚合版本失效。

## 9. 基线预审发现

以下问题来自对当前设计基线的静态预审，应在实现开始前明确关闭方式。

| ID | 级别 | 发现 | 建议处理 |
| --- | --- | --- | --- |
| RF-REV-001 | P1 | 8.1 伪代码先校验 OPEN，再检查本人已有决定；与 5.3、7.3 的“先处理已有决定”不一致 | 固定为：身份和归属校验 → 查询已有决定 → 同语义重放/冲突返回 → 校验 OPEN → 新增决定 |
| RF-REV-002 | P1 | 提交和审核状态更新未明确推进 `contents.lock_version`，旧标签页可能在内容被拒绝后以旧版本成功覆盖 | 规定所有 content 状态或工作副本变更均递增版本，并增加跨轮次旧标签页测试 |
| RF-REV-003 | P1 | “历史不可变”主要依赖无更新接口，具体 GRANT 尚未在 DDL 中体现 | migration 中按表授予最小权限，应用账号对 revision/decision 只获得所需 SELECT/INSERT |
| RF-REV-004 | P2 | `SELF_REVIEW_FORBIDDEN` 当前定义为 409，授权语义也可采用 403 | 在 OpenAPI 中做一次明确选择，保持所有实现和测试一致即可 |
| RF-REV-005 | P2 | 幂等记录清理只有索引，没有保留期限和运行策略 | 定义保留期、清理批次和“业务历史不随幂等记录删除”的规则 |
| RF-REV-006 | P2 | 设计要求严格 Schema，但未明确所有 Zod object 是否启用 strict | 契约测试必须证明未知身份及状态字段返回 400 |

当前架构方向无需推倒重做。前三项属于实现前必须关闭的正确性或防线问题。

## 10. 问题分级和处理规则

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 可导致越权、历史篡改、双终态或不可恢复的数据错误 | 立即阻断，修复并重新完整评审 |
| P1 | 核心流程在重试、并发或失败条件下不可靠 | 合入或实施前必须修复并补测试 |
| P2 | 可维护性、可观测性或契约一致性不足，但不立即破坏核心不变量 | 记录负责人和截止版本，可有条件通过 |
| P3 | 命名、文档表达或非阻断优化 | 纳入普通待办，不影响结论 |

每条问题必须包含复现条件、影响、不变量映射、处理决定、负责人和验证证据。只写“已修复”不能关闭问题。

## 11. 评审结论标准

### 11.1 通过

- 无未关闭 P0/P1。
- 14 条不变量均有实现位置、数据库防线或测试证据。
- 核心并发和回滚测试在真实 PostgreSQL 上通过。
- migration、seed、构建和自动化测试可从空环境重复执行。

### 11.2 有条件通过

- 无 P0。
- P1 已有明确修复方案、负责人和合入门禁，但证据尚待补齐。
- 遗留项不改变领域模型或事务边界。

### 11.3 不通过

满足以下任一条件即不通过：

- 身份可由客户端指定或旁路写入。
- 历史 round 读取可变 content。
- 同一 content 可以存在多个 OPEN round。
- 审核终态依赖无锁的先查后写。
- decision、round、content 和幂等结果跨事务提交。
- 并发正确性只靠文字推断或 mock 测试。
