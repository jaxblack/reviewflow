# ReviewFlow P0 安全与一致性审查

## 结论

本次审查发现并修复 1 个 P0：公开 Demo 的持久化写入没有容量和速率边界，匿名访问者可以持续消耗数据库存储与主机资源，并影响同机其他服务。

修复后未发现其他 P0/P1 阻断项。生产依赖和全部 npm 依赖的 critical、high、moderate、low 漏洞均为 0。

## 威胁模型

- ReviewFlow 通过公网 HTTPS 提供演示。
- 用户切换是明确的 Demo 功能，访问者可以切换至包括 ADMIN 在内的预置身份。
- 数据库只允许保存演示数据，但服务器还运行其他服务。
- 应用只监听回环地址，由同机 Caddy 代理。
- 当前生产运行一个 Node.js 实例和一个 PostgreSQL 16 主库。

“能够切换身份”本身不作为漏洞；利用公开写接口无限消耗主机资源属于漏洞。

## 已修复 P0

### SEC-P0-01：无限持久化写入导致磁盘耗尽

攻击者无需 Cookie 即可使用默认 Alice 身份，持续使用随机 `Idempotency-Key` 创建最大 50,000 字符的内容。每次成功请求同时增长业务表和保存完整响应的幂等表。攻击者还可以切换身份，持续创建用户、编辑内容及追加审核轮次。

影响包括：

- PostgreSQL 业务表、索引和 WAL 持续增长。
- 写事务持续消耗 CPU 和 I/O。
- 主机磁盘耗尽后，ReviewFlow、同机服务、日志和系统更新都可能失败。

### 修复

| 防线 | 默认值 | 行为 |
| --- | ---: | --- |
| 共享 IP 写入限流 | 30 次/分钟 | 会话切换和所有持久化写接口共用额度，超限返回 429 |
| 用户数量 | 100 | 达到上限后禁止创建用户 |
| 内容数量 | 500 | 达到上限后禁止创建内容 |
| 单内容轮次 | 20 | 达到上限后禁止继续重新提交 |
| 未过期幂等记录 | 2,000 | 达到上限后禁止新的持久化写入 |
| 幂等保留窗口 | 24 小时 | 过期记录在后续写事务中回收 |

Fastify 只信任来自 `127.0.0.1` 和 `::1` 的代理地址，公网客户端不能直接用 `X-Forwarded-For` 选择限流身份。配额计数和业务写入位于同一个 PostgreSQL 事务中，并使用行锁或唯一约束阻止并发请求同时越过上限。

## 验证证据

- 达到内容、用户或每内容轮次上限时返回 `507 CAPACITY_LIMIT_REACHED`。
- 达到上限的失败请求不会新增内容、快照、轮次、决定或用户。
- 同一代理 IP 跨会话切换、内容创建和编辑共享限流计数，超限返回 `429 RATE_LIMITED`。
- 幂等表达到上限后拒绝新写入；超过 24 小时的记录可被回收。
- 真实 PostgreSQL 测试锁定容量计数、关系约束、事务失败回滚和并发竞争后的最终数据库事实。
- 双进程测试使用独立 Fastify/`pg.Pool`，通过确定性屏障覆盖 9 个竞争场景。

## 已排除 P0/P1

| 类别 | 排除依据 |
| --- | --- |
| SQL 注入 | 所有外部输入使用参数绑定；动态 SQL 片段只来自固定服务端常量 |
| 存储型 XSS | 用户内容通过 React 文本节点输出，不使用 `innerHTML` 或 `dangerouslySetInnerHTML` |
| CSRF 权限提升 | 写接口要求 JSON，Cookie 使用 SameSite=Lax；身份切换本身是公开 Demo 能力 |
| 身份和角色绕过 | 每次写入从签名 Cookie 和数据库重新读取角色，并校验作者和状态 |
| 审核终态分叉 | content → round 固定行锁顺序串行化终态计算，失败请求整体回滚 |
| 历史快照泄露 | 非作者审核人只能看到已提交快照，不能看到被拒绝后的未提交工作副本 |
| 部署命令注入 | 部署只接受已验证的 main SHA，release ID 有严格格式白名单，参数均引用 |
| 运行时依赖漏洞 | `npm audit` 对生产及全部依赖均报告 0 漏洞 |

## 残余风险

以下项目未达到 P0/P1，不在本次修复范围内：

- 应用级 IP 限流是单实例内存状态，进程重启后计数清零；硬容量上限仍然生效。
- 分布式来源可以绕过单 IP 限流，但不能绕过 PostgreSQL 事务内的业务容量上限。
- 已验证两个应用进程共享一个 PostgreSQL 主库，但尚未演练主从故障转移、网络分区、磁盘满和备份恢复。
- 当前身份切换不能用于真实业务数据，生产系统仍需接入组织身份认证。

## 运维要求

1. 保持应用只绑定 `127.0.0.1`，不得直接暴露 Node 端口。
2. 保持 Caddy 为唯一可信代理，不扩大 Fastify `trustProxy` 范围。
3. 调整容量环境变量前先检查当前 PostgreSQL 表大小和演示数据量。
4. 收到 507 时先执行 `pg_dump` 并检查容量计数，不要简单提高上限。
5. 定期验证备份可恢复，并监控连接数、慢事务、主机磁盘和 PostgreSQL WAL。
